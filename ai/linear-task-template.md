# Шаблон задачи Linear (Swoosh Server)

Каждая задача по этому репозиторию оформляется по структуре ниже. Язык — русский.
Заголовок — короткий и по делу; вся конкретика в теле. Скилл `linear-tasks`
использует этот файл как источник структуры при создании задач.

Пустые/неактуальные секции удаляй, не оставляй заглушки. Секции, помеченные
_(опционально)_, добавляй только когда есть что написать.

---

## Порядок _(опционально)_

Место задачи в цепочке работ и предусловия. Пиши, если задача — часть большего
потока или зависит от другой.

- Этап: например «Интеграция, шаг 2».
- Предусловия: что должно быть готово до старта — со ссылками на связанные задачи,
  эндпоинты, спеки.

## Зачем

Причина задачи: какая проблема сейчас, какое поведение должно появиться или
сохраниться. Один-два абзаца, без воды. Фокус на наблюдаемом результате для
пользователя/системы, а не на реализации.

## Что сделать

Нумерованный список конкретных шагов. Каждый пункт — техническая специфика:

- какой модуль / эндпоинт / поле / DTO трогаем (указывай пути `src/...`);
- какие состояния и крайние случаи покрыть (loading/ошибка/пустой ответ/потеря сети);
- как ошибки и валидация ложатся на конкретные поля, а не «в общий баннер»;
- что **НЕ** делать (легаси не расширяем, дублирующую защиту не плодим и т.п.);
- совместимость: что не должно сломаться в текущем контракте.

1. …
2. …
3. …

## Готово когда

Критерии приёмки — наблюдаемое, проверяемое руками или ревью поведение
(не «сделано», а «эндпоинт возвращает X при Y»).

- …
- Проверен happy-path и ключевые ошибки (сервер вернул ошибку, потеря сети, невалидный ввод).

## Риски и крайние случаи _(опционально)_

Что может отломаться, скрытые зависимости, миграции данных, обратная совместимость
контракта, порядок деплоя.

## Вне скоупа _(опционально)_

Что сознательно НЕ входит в задачу — чтобы не расползалось. Смежное выносим в
отдельные задачи со ссылками.

## Обязательно проверить и обновить

Отметь актуальное; неактуальное — удали.

- [ ] `ai/superpowers/` — spec (если меняется поведение/контракт) + plan, одним коммитом ДО кода (см. секцию Workflow в `AGENTS.md`)
- [ ] `README.md` — если менялся сетап, запуск или переменные окружения
- [ ] `ai/rules/*` — если менялись правила архитектуры или контрактов
- [ ] `ai/skills/*` — если материально изменён backend-паттерн (AGENTS.md требует апдейт в том же изменении)
- [ ] `ai/map.md` — если добавлен/удалён/переименован модуль, common-пакет или entry-файл (включая список «чего в проекте НЕТ»)
- [ ] `ai/decisions/` — новая датированная запись, если задача зафиксировала или отменила долгоживущее решение
- [ ] Swagger (`*.swagger.ts`) — при изменении публичного API-контракта
- [ ] `.env.sample` — при новых переменных окружения

## Проверка

- [ ] `npm run lint`
- [ ] `npm run build` — после удаления файлов, смены зависимостей или изменения контрактов

Автотестов в проекте нет — верификация линтом, билдом и ручным разбором по `ai/rules/`.
