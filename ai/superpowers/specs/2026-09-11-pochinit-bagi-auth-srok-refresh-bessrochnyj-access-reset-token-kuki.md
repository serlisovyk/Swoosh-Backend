# Spec: auth-баги — срок refresh, бессрочный access, reset-токен, куки

MY-53 · 2026-09-11

## Зачем

Ревью `src/modules/auth` вскрыло шесть дефектов: один ломает вход прямо сейчас
(рассинхрон env-переменной), три — дыры в безопасности (бессрочный access,
reset-токен с legacy-форматами и без атомарного гашения, тайминг-энумерация),
ещё два — контрактные баги (перевёрнутый `sameSite`, гонка при регистрации).

## Меняемые контракты

### 1. Источник срока жизни refresh-токена

- Было: `JWT_REFRESH_TOKEN_EXPIRES_DAYS` (число дней, `getOrThrow`) для куки +
  `JWT_REFRESH_TOKEN_EXPIRES_IN` (строка `ms`, `get`) для подписи JWT — два
  независимых источника, первого нет в `.env`.
- Стало: только `JWT_REFRESH_TOKEN_EXPIRES_IN` (строка формата `ms`, как
  `"1d"`). Срок куки считается из неё же через `ms()`. Оба чтения —
  `getOrThrow`.
- `.env.sample`: убрать `JWT_REFRESH_TOKEN_EXPIRES_DAYS` и мёртвый
  `JWT_ACCESS_TOKEN_EXPIRES_HOURS`.
- Локальный `.env` уже содержит `JWT_REFRESH_TOKEN_EXPIRES_IN="1d"` — новый
  контракт валиден на этом стенде без правок `.env`.

### 2. `expiresIn` для access и refresh — обязателен

`configService.get` → `configService.getOrThrow` для
`JWT_ACCESS_TOKEN_EXPIRES_IN` и `JWT_REFRESH_TOKEN_EXPIRES_IN`. Отсутствие
ключа теперь роняет запрос (500), а не выпускает вечный токен.

### 3. Reset-токен: только HMAC, атомарное гашение

- `findByPasswordResetToken` ищет только по `hashTokenWithSecret(token,
RESET_TOKEN_SECRET)` — убрать поиск по `sha256`-без-секрета и по сырому
  токену.
- `hashToken` (sha256 без секрета) удаляется из `auth.utils.ts` — после
  правки нигде не используется.
- Поиск и гашение объединяются в один атомарный `findOneAndUpdate`
  (`resetPasswordToken: hashedToken` → `null` + `resetPasswordTokenExpiresAt:
null`), возвращающий документ **до** обновления. Второй параллельный запрос с
  тем же токеном не найдёт совпадения — токен уже погашен первым.

### 4. Cookie `sameSite`/`secure` — прод и dev меняются местами

Фронт и API живут на разных сайтах (подтверждено в задаче):

- **Прод** (`isDev` = false): `sameSite: 'none'`, `secure: true` — кросс-сайтовый
  запрос иначе не донесёт куку.
- **Dev** (`isDev` = true): фронт и API на `localhost` (разные порты — тот же
  site), `sameSite: 'lax'`, `secure: false` — по http `secure: true` куку не
  поставит.

`secure` перестаёт быть константой `true` и зависит от `isDev`, как и
`sameSite`.

Новый decision record объясняет, почему `none` в проде — это следствие
раздельных доменов, не небрежность.

### 5. Тайминг-энумерация в `validateUser`

Когда пользователь не найден, выполняется фиктивная `argon2.verify` над
константным хэшем (не над реальным паролем — реального хэша нет), прежде чем
бросить `UnauthorizedException`. Время ответа перестаёт зависеть от ветки
"пользователь есть / нет".

### 6. Гонка при регистрации

- Уникальный индекс на `email` уже есть в `User` схеме
  (`src/modules/user/models/user.model.ts:11`, `unique: true, index: true`) —
  добавлять не нужно.
- `UserService.create`: домашняя проверка `getByEmail` остаётся как быстрый
  путь (без индекса задержка на дубликат была бы только в момент записи), но
  добавляется перехват ошибки дубликата (`code === 11000`) из
  `userModel.create` → `ConflictException(USER_ALREADY_EXISTS_ERROR)`. Два
  параллельных запроса: один пройдёт, второй получит 409 от индекса, а не 500.

## Риски / переходный период

- Смена `sameSite`/`secure` не ломает уже выданные куки обратной
  совместимостью — браузер просто применяет новые атрибуты к новой куке;
  старые истекут по своему exp. Не требует специальной миграции.
- Смена источника срока refresh-куки — контракт окружения: `.env.sample`
  обновлён в этом же коммите; локальный `.env` уже соответствует.
- Удаление legacy-веток reset-токена инвалидирует ссылки, выданные в старом
  формате, до раскатки — окно 30 минут (TTL токена), риск незначительный.
- Фиктивная проверка хэша в п.5 использует `argon2.verify` с тем же
  cost-параметрами, что и реальная — не должна быть заметно быстрее/медленнее.

## Вне скоупа

- Ревокация refresh-токенов / token version / blacklist — новое решение,
  не эта задача.
- Усиление политики паролей.
- Рефакторинг структуры модуля.
- Глобальный `AllExceptionsFilter` под целевой error envelope — сервисы
  продолжают бросать built-in Nest-исключения.
